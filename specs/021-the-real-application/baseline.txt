== CAUSES READ FROM SOURCE (certain, not inferred) ==

  1. De-duplication is per ELEMENT, not per question.
     page_answers.build keys rows on field_core.key(descriptor)
     = (descriptor["doc"], descriptor["je_idx"]) — a per-element stamp.
     Two elements serving one question => two rows. A Workday dropdown is a
     trigger with aria-haspopup=listbox PLUS the listbox, both matched by
     FIELD_SELECTOR, so this is guaranteed on every dropdown.

  2. A whitespace label is accepted as a question.
     ext_backend.question_of() is
       label_text or placeholder or aria_label or ""
     with NO .strip(). " " is truthy in Python, so the row is created and
     panel.js renders it blank. There is also no automation_id fallback,
     even though scanner.js describe() already captures data-automation-id
     — which is exactly where Workday puts a field's stable identity.

  3. The index is never pruned.
     _page_entries[job_id] is cleared only in _start_answer_feed. Keys are
     (doc, je_idx). je_idx lives in a DOM attribute, so a React remount
     gives fresh stamps and NEW entries while the old ones stay. The doc
     token is on documentElement and does not change. A multi-step Workday
     application therefore accumulates monotonically.

  OPEN until the real capture (T012): is "Seen 156" one scan genuinely
  seeing 156 descriptors, or _frame_seen summing stale frames?
  _frame_seen[frame_id] = seen is an ASSIGNMENT (per-scan per-frame), but
  the dict is cleared only at session start, so a frame that disappears
  leaves its count in the sum forever.

== AI SPEED: TWO HYPOTHESES TESTED AND DISCARDED ==

  1. "GPU offload is silently hurting."  NO.
     .venv llama_cpp 0.3.34 ships exactly:
       ggml-base.dll  ggml-cpu.dll  ggml.dll  llama.dll  mtmd.dll
     No CUDA, Vulkan, SYCL or Metal backend. n_gpu_layers=-1 is INERT on
     this install. Not a lever.

  2. "Thread misconfiguration."  Already measured in 020:
     8/4/3 threads -> 22.9 / 23.2 / 24.0 s. Flat. Memory-bandwidth-bound.
     Not a lever. Do not re-attempt.

  Carried from 020, treated as fixed constants:
    generation      ~5-6 tok/s
    prompt eval     ~42 tok/s
    one AI analysis ~66.8 s

  Tailoring cost, derived: summary + 4-6 bullets + ~180-word cover letter +
  keywords ~= 500-700 output tokens = 100-140 s of generation ALONE, plus
  ~36 s prompt eval. So 2.5-3 minutes on-device, inside its 300 s budget
  ONLY when nothing is queued ahead of it — and upgrade.py stands down for
  fill sessions but NOT for a tailor request.

  THE ACTUAL LEVER, already shipped and switched off:
    matcher.DEFAULT_BASE_URL = https://api.groq.com/openai/v1
    matcher.DEFAULT_MODEL    = llama-3.3-70b-versatile
    _min_interval() = 2.2 s  (~28 req/min, under the free tier's 30 RPM)
  But scoring_tier() returns "local" whenever local_llm.available() and
  PREFER_LOCAL_LLM != "0" — and it defaults ON. Saving a key changes
  NOTHING today, and nothing in the UI says so.

  Free tier is also ~1K requests/day, so bulk work must stay local. 020
  already made bulk ranking model-free, so there is nothing to lose.

  T029  STALE FRAMES — the open question, answered by construction

    _frame_seen was frame_id -> count, cleared only at session start. An
    iframe that navigated away or was removed left its count in the sum
    FOREVER. Now (count, monotonic) with a 30 s staleness window.

    The page report carries BOTH numbers — counts.seen (live frames) and
    counts_reported.seen_all_frames — so when the applicant captures their
    real page, the gap between them IS the inflation, measured rather than
    argued about.

  T106  EXTRACTION PROMPT, AFTER ADDING THE HISTORY FIELDS

    _SYSTEM                 1332 chars   (was ~1180)
    CHUNK_TARGET_CHARS      5000
    MAX_LOCAL_PROMPT_CHARS  6000
    worst case total        7332 chars  ~= 1900 tokens
    model context           8192 tokens

    The "6k" figure in resume_extract.py bounds the CHUNK, not the assembled
    prompt; the pre-021 worst case was already ~7180 and v2.0.0 shipped with
    it. Still comfortably inside the context. Pinned by a test at < 2000
    chars for _SYSTEM and < 8000 for the worst case so it cannot creep.

  T060  ON-DEVICE TUNING — BOTH LEVERS ARE DEAD ENDS, MEASURED

    Same model (qwen2.5-1.5b-instruct-q4_k_m), n_threads=8, n_gpu_layers=0,
    warmed, 180 output tokens of prose:

      n_ctx=8192 (today)   18.0 s   180 tok    9.97 tok/s
      n_ctx=4096           19.2 s   180 tok    9.38 tok/s
      n_ctx=2048           20.8 s   180 tok    8.66 tok/s

    Shrinking the context makes it SLOWER, not faster. Rejected.

      n_ctx=4096 + type_k=q8_0/type_v=q8_0
        -> ValueError: Failed to create llama_context

    KV-cache quantization cannot even build a context on this llama_cpp
    0.3.34 CPU build. Rejected. (This was analysis finding A9 and it landed
    exactly as predicted, which is why it was measured before adoption
    rather than shipped behind a retry.)

    CORRECTION TO THE 020 FIGURE, worth carrying forward: 020 recorded
    generation at ~5-6 tok/s. That was measured on the full analysis schema
    — GRAMMAR-CONSTRAINED JSON. Free prose on the same model measures
    ~10 tok/s. Both numbers are right; they are different workloads. The
    cover letter is JSON-mode, so it does run at the slower rate.

    CONCLUSION: there is no on-device multiplier available on this CPU.
    The two levers that are real are (a) the free cloud tier, which already
    shipped and was switched off, and (b) asking for fewer output tokens —
    and (b) is now applied ONLY on the on-device path, because cutting
    quality on a path that already answers in seconds would be a bad trade
    made for no reason.

  T058  STREAMING TAILORING — REJECTED ON INSPECTION, NOT ATTEMPTED

    The plan said "stream tailoring output so text appears as it is
    generated". It cannot usefully do that: TailorResult is a pydantic-
    validated JSON OBJECT, so a partial stream renders as
    {"summary_line": "Comp — which is worse than a spinner, not better.

    What the applicant actually reported is that the button did nothing at
    all. That is fixed at its two real causes (the throwing JSON.parse, and
    the FIFO queue), and the handler now ALWAYS writes a message. Recorded
    here rather than silently dropped.
