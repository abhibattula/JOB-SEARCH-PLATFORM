  _score_new_jobs() runs inline in _post_ingest (engine/pipeline.py:156),

== FEED LISTING QUERY (22,145 rows) ==

  FIRST MEASUREMENT WAS WRONG — recorded here so the mistake is traceable.

  A hand-written query with NO date window measured 67.9 ms and planned as
  USE TEMP B-TREE FOR ORDER BY, and the plan claimed an expression index
  would take it to single-digit ms. The app never runs that query:
  db.query_jobs() always applies a window (14 days by default) and defaults
  to sort="score", whose ORDER BY leads with match_score — which an index on
  the date expression cannot serve at all.

  MEASURED PROPERLY via db.query_jobs() against a copy of the real database,
  median of 5 runs, with and without the candidate index:

    view                                        today    with index
    default: 14d + entry-level + score sort     22.3 ms    23.6 ms
    all window + entry-level + score sort       27.1 ms    24.5 ms
    all window, no entry filter, score sort      332 ms     318 ms
    all window, no entry filter, DATE sort       329 ms     153 ms  <-- 2.1x

  => The default view was never slow. The index is worth 2.1x on exactly one
     view (the widest listing, date-ordered) and is neutral elsewhere.
     FR-022 and SC-009 were rewritten to this measurement. See research R7.

  A composite (match_score DESC, COALESCE(posted_date, first_seen) DESC)
  index was also built and measured: no improvement on any view, because the
  dynamic WHERE clause stops SQLite using it for ordering. Rejected.

  needing-score scan (600 rows)   9.4 ms

== T010 RESULT: RANKING THROUGHPUT (post-change) ==

  Budget (SC-002): the whole eligible backlog ranked in under 30 s, no model.

  627 eligible jobs, end to end through pipeline._rank_new_jobs():

    first implementation   11.48 s   (18.32 ms/job)
    after batching writes   0.66 s   ( 1.05 ms/job)   <-- 17x

  The first number was NOT the matcher. basic_match itself measured
  0.0044 s/job standalone; db.set_match opens a connection and commits per
  call, so 627 jobs meant 627 WAL commits. db.set_matches() writes one
  transaction per chunk instead.

  Caveat on comparing the two figures honestly: the standalone benchmark used
  a ~2900-char resume and a ~2900-char JD, the harness uses shorter text. A
  realistic worst case is therefore a few seconds, not 0.66 s. Either way it
  is far inside the 30 s budget, and against the pre-020 local tier's
  measured 66.8 s/job the same 627 jobs were 11.6 HOURS.
